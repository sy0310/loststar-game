## 3. 拼图货舱：让装载本身成为一个小选择

### 3.1 容量和形状

初始4×4、16个小格。原容量4作为兼容体积单位，每个原单位对应4个小格：
- 原size=1 → 4格：2×2、1×4、L形、T形等，按物件实际轮廓指定，不要全部变方盒。
- 原size=2 → 8格：2×4或另一个经过审核的连通8格形状。
- 委托记录箱固定2×2，占4格，保留其不可出售身份、原丢弃后果与正常交付行为。
- 原schema允许size=3/4，兼容迁移需要支持12/16格，不得只写新事件当前用到的1/2。
- area(mask)=4*legacySize。4×4不是免费扩为16件货；价格/价值/作用不随换算变化。
- 已安装扫描仪、绞盘属于船体工具，不突然占货舱。油箱与船体耐久也不是新增的可搬动物品。
- 允许90度旋转，不允许镜像变形、缩放作弊、重叠、越界或跨锁定区域。相同物品使用稳定shapeId/shapeVersion；摆放不调用随机数、不改变后续路线。

位置可以用归一化格点mask、x/y、rotation表达；货物绑定原uid，而不是数组下标、物品名或DOM节点。用稳定的显示分类/资源ID，不要靠中文名称正则猜形状。

默认不开放新扩舱收费。本轮先测原面积下的装载。如果形状约束明显过严，报告装载失败率与例子，不偷偷增加格子或提价解决。

### 3.2 手机操作

- 获得货物时显示其占格轮廓、用途和已知价值；不会提前展示未到达航点的掉落。
- 在货舱中可拖动，松手吸附网格；预览要有合法/不合法轮廓和符号，不只依赖红绿颜色。
- 必须有单手等价操作：点选货物→点击旋转按钮→点目标格放置。不能只支持桌面右键或两指手势。
- 提供可选“一键整理”作为辅助，不默认自动重排每次新货。搜索完整可行布局，在本16格规模内给明确成功/无法装入结果，不得把贪心失败说成绝对放不下。
- 默认一件货一个图标/轮廓，不是在占用的每个格子里复制一张图。物件细节图与格子边界协调，不能把概念海报截图当整块货物贴图。
- 选中后下面显示名称、占格、已知售价/作用。现有出售、使用、放弃照原规则开放。
- 拖出边界或点错位置只回到原位置，不能默默销毁。丢弃/出售需要明确入口；丢弃委托物保留后果确认。
- 货舱界面关闭不改变阶段、不给奖励、不自动返航。移动/旋转已提交位置刷新恢复；取消布局草案恢复上一个合法布局。
- 格子触控应适合360/390竖屏，可优先采用约48 CSS像素以上的格子与至少44的独立操作触区；允许随可用宽度计算，不写死导致小屏溢出。指针取消、系统返回、拖动滚屏、减少动态均有处理。

### 3.3 获取货物的提交顺序（必须一次性结算）

不能先扣钱/扣耐久，才告诉玩家“新形状放不下”；也不能因为取消摆放重复获得奖励。

优先方案：
1. 用户选择已展示的事件选项；如有新货，先以只读draft展示完整待装载布局与当前已知后果。
2. 玩家可以在draft中重排、明确选择弃置旧货，或取消；不收费、不推进随机数、不改变持久事件。
3. 点“确认装载”时，控制器在同一次带revision/nonce校验的原子事务内验证费用、燃料、几何布局、物件来源、弃置后果和所有新货；然后执行选择、风险抽取、账本、货物UID与布局提交一次。
4. 未提交的随机风险结果不得提前揭示；重排或取消不能洗结果。若原规则最终触发救援，仍由原救援逻辑结算，不让草案绕过死亡/丢货规则。
5. 没有获得货物的选择继续直接执行；带移除/销售的选择按变更后的货物集合验证。多个待得物品必须整批验证，不半装半扣。

不增无限“暂存仓”。现有货物始终属于原货舱；未提交新货不算已拥有、不能使用/出售/触发后续事件。候选布局只在当前事件事务内存在。多标签发生竞争时保留已提交数据，提示重开布局；不能覆盖别人新余额或装载。

### 3.4 旧存档迁移（安全优先）

当前引擎SCHEMA=2、capacity=4、独立KEY=lostcargo.route-demo.v1。增加schema版本与纯迁移函数，继续使用原存储控制器与事务；不要改个库名就让当前玩家重开。

- 迁移前保留原始备份，先在副本校验，再原子写入；失败保留原档可导出，不自动create()。
- 所有uid、name、value、ability、story、contract、acquiredRun与账本原值不变，路线/RNG/深度/距离/报价不变。
- 新shape组合可能无法装下旧总容量合法货物。对此不得静默丢货/溢出/把货丢到免费仓。采用明确标记的legacy-packed运输包装：size=k时2行×(2k格面积)的可拼矩形组合，例如size1=2×2、size2=2×4、size3=由3个2×2块组成的12格连通形、size4=4×4，按固定2×2分区给全部旧货合法落位。包装仍可出售/使用且价值不变。
- 对旧货想改为标准轮廓，只在用户主动重整且全货能够合法放入后确认，无收费；新获得物品用标准shape。
- 扩充validateCargo/assertState/restore/import/export，兼容真实事件context.cargo快照、result、summary、历史archive元数据。不能把本来合法的旧事件快照因为没有实时摆放坐标而拒绝。
- 出发记录箱也必须参与几何装载检查。返航交付/取消出发/卖货/使用/救援删除物件时同步释放格子，不留幽灵占位。

## 4. 航路必须是地图，不是8个圆点或一个假Tab

### 4.1 四主入口维持不变

维持“港口（航行中为当前航行） / 航路 / 货舱 / 航记”。不再加第五个地图入口。

新增真正独立的tab=route渲染：不能继续把route映射为play；地图页对港口、选路、事件中、结果、返港状态都有合法表现。

### 4.2 地图可见内容

- 出发港为明确房屋/停泊节点。
- 已走航点以实线连接、真实类型图标、简短地名显示。
- 当前点使用小飞船或定位环，不和“下一站”混淆。
- 下一步两条真实候选分叉以虚线呈现；点击节点选中，不立即扣油，下方复用同源quote的确认卡。
- 更远的未扫描部分只用中性虚线/省略号和“本趟最多8站”表达，不预先生成/公布未来节点身份、稀有物、结果或新星球。
- 清楚显示“已走n/8”和返回母港的虚线引导航路；返航费用来自homeCost(state)，不是按屏幕线长计算。
- 信息优先级：我在哪里→下一步能去哪→去那以后还能否回来。地名、节点类别、燃料图标同时存在，不仅靠颜色。

不要画一个与逻辑无关的装饰性星图。历史从history/legs/真实保存快照读取，候选直接来自state.route。未选择的旧支线只有确有快照才保留为“已错过”，不得事后重新掷骰子补造。

事件中查看地图是只读导航：可以回当前事件或按原规则确认放弃返航，不得跳过事件直接travel。地图选中态不是状态提交，取消不扣费。航次结束地图保留刚走路径；下一次合法depart才重置本趟路线。

### 4.3 视图要求

采用纵向可滚动的一张航路图，当前点与下一分叉进入视口，避免一屏压下8层小字。不用缩放/旋转操作；节点触区与标题可读，手机顶部摄像头和底部手势区避让。

从事件→货舱→航路→事件返回时保留选择、滚动和待处理上下文，地图/货舱操作不得触发底层事件选择。

## 5. 一套原创图标，贯穿顶部、按钮、航点与结果

统一采用仓库内的SVG图标组件或明确的新原创图标目录，不使用emoji/Unicode文字符号替代正式图标，不从参考游戏提取素材。保持已认可紫灰UI、暖金主操作，边框/大小/线重一致。

|语义|候选图形|出现位置|
|---|---|---|
|燃料|油滴/油罐|资源条、前进、返航、补给、费用结果|
|船体耐久|盾牌/船壳|资源条、风险、维修、损伤结果|
|零件|螺母/齿轮|余额、支付、售价、还款，不换成新金币|
|货舱|网格货箱|容量、装载预览、货舱导航|
|港口/补给|停泊标/补给塔|航点、返港、购买|
|残骸回收|残骸箱/机械夹|已知地点类别与安全回收选择|
|异常信号|波纹/雷达|未识别信号，不能暗示隐藏怪物|
|风险/警告|警示三角|已知风险和无法出发原因|
|旋转/整理|90度弯箭头/排列|拼图操作|
|离开/返航|方向箭头/母港|保留不同语义文字|

事件页继续“图片＋短文字＋2～3选项”。事件标题带类别图标，选项带动作图标和费用chip，结果显示真实增减图标；服务节点原少量4选项不为统一排版删掉。

费用chip读取实际支付/受上限约束的增量与已有风险范围，不能机械照设计图数字。未知结果保持未知，不用图标泄露未来内容。图标配文字，屏幕阅读标签明确；不靠绿色唯一表示可操作。SVG无外网字体/CDN依赖。

## 6. 代码落点与实施顺序

建议分工，不强制推翻现有文件架构：
- cargo-layout.js：纯函数mask/旋转/碰撞/布局校验/迁移/自动整理；engine.js调用，不能只有UI检测。
- engine.js：提交布局、交易/获得/离港/返回/救援/导入校验和schema兼容；money与fuel公式保持原源。
- app.js：cargo网格与选择流程、独立route tab、费用与资源图标，移除route→play映射。
- icons.js或assets/icons/：一套语义图标，所有页面复用。
- styles：同主题下的格子、选择轮廓、地图线和节点；保持真实安全区。
- 原持久化模块：继续使用原子提交、多标签revision和保存失败保护；不另写绕过存储层的拖拽保存。

顺序：先核对现有原子状态层→纯几何与迁移测试→货舱手机交互→真实地图与图标全链→固定ZIP两趟回归→新TapTap开发自测。用户已授权这些明确改动，无需仅交设计稿或每个按钮停下来确认；超出范围的平衡、收费、自动战斗另提，不擅加。
