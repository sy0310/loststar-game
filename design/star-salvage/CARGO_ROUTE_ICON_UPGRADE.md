## 1. CARGO：4×4可操作货舱，先保持体积预算

### 1.1 初版确定的模型

- 默认4列×4行，共16个小格。原4格是抽象体积单位，不能把原1格物件直接改成1小格、暗中将承载能力放大4倍。
- 首轮映射：原size=1物件占4小格；原size=2物件占8小格。现有测绘记录箱原size=1，建议2×2；返港交还后占格释放，原委托条件/奖励不变。
- 新回收货按材质设计稳定轮廓，例如1×4长条、2×2方形、L4、T4；大件优先2×4。它们是占格轮廓，不能只是给同一个矩形背景换颜色。至少3种明显不同的4格轮廓和1种8格轮廓出现在可操作测试中。
- 形状、旋转和位置属于真实规则；空格总数够不代表形状能塞下。对玩家显示“已用12/16小格”，不再同时出现“还剩1大格”和小格混算。
- 物品图必须与其占格边界可辨，空缺的L形角可以放别件物品；不因图像透明外框把空洞也算碰撞。每件按稳定item/shape ID注册，不能以随机名称决定形状。
- 原货值、能力、出售/消耗规则、acquiredRun、唯一uid全部保留。船上油箱内燃料和永久安装工具不突然变成占货舱物件；只有实际已有货物参与排布。
- 不加扩舱升级。本轮只替换体积表达并引入几何约束。空间约束会改变可带回的价值，因此须重新比较原版/新版货量、弃货率、收益，不能只凭面积等价声称经济不变。确需调整形状分配时记录前后与原因，不靠涨价或减返航储备补平衡。

### 1.2 操作与手机可用性

- 一次点选物品，再点目标格可移动；同时支持拖动吸附。触屏不强制双指，也不依赖右键或悬停。
- 选中后有明确“旋转90°”“放置/确认”“取消”控件，四次旋转回到原形。不加镜像翻转，除非物件本身声明支持。
- 预放位置同时给轮廓/符号和文字状态：可放、重叠、越界；颜色只是辅助。取消、拖出区域、pointercancel、失焦均不得让物件丢失或凭空复制。
- 360/390竖屏下每个操作格建议不小于48 CSS px；给手指遮挡留预览偏移或上方小轮廓。处理多指、页面滚动、拖拽与单击的互斥；只在网格/被抓物件上接管手势，不禁止整页滚动。
- 已确认排布随存档保存。编辑草稿不改余额、体积、随机数或旧确认排布；取消恢复原排布。
- 不将“一键最优整理”放成默认主操作。可以取消本次编辑，但先保留手工收纳的意义；不加装箱计时/手速惩罚。

### 1.3 新货获得与容量不足：必须闭环

- 事件选项先展示已知代价与新货轮廓/占用；若货物仍未知，先用通用包裹轮廓，不提前揭露未发生的剧情。已满不等于强制丢旧货，玩家可以主动放弃新发现。
- 建议两阶段事务：确认回收时，原事件费用/风险/随机结果只结算一次，并把实际待装新货写入持久pendingCargo；随后进入装载界面。关闭/重开仍是同一已解决事件，不再次扣费、损伤、抽结果或生成货物。
- 最终确认排布才把选择带走的新货变为正式cargo/收藏取得记录；待装货不能提前出售、使用、满足连续奇遇的“实际携带”条件或计入未售货值。结果页可说“已回收，待装载”，不能先宣称全部入舱。
- 待装载或临时整理区不是额外运输空间。继续航行/正常返航前必须明确完成装载，或确认放弃未装新货；不能将区外物品带走。返航按钮不能失效到卡死，要提供“放弃未装新货并返航”的明确确认。
- 整理时暂挪出的旧货只有草稿状态；关闭应恢复旧排布，除非玩家明确确认弃货。已拥有、已承诺携带的旧货不能因新货无法摆下自动被卖掉或丢掉。
- 货舱满时至少提供：调整位置/旋转、放弃本次新货、确认抛弃选定旧货。使用或出售必须遵守原场景规则，港外不凭空提供随时卖货。
- 高风险回收导致耐久归零时，先按原救援规则处理；pending新货不能在救援后重新领取。保留acquiredRun区分本趟新货与跨趟旧货。

### 1.4 旧档迁移和并发

- 当前SCHEMA=2、KEY=lostcargo.route-demo.v1。新schema升级原数据结构，不改namespace导致看似新开局。迁移前保留原字节备份；验证完整新数据后一次提交，失败原档不变。
- 新增cargoGrid及每件uid对应placement/mask/rotation等字段；布局必须验证唯一UID、合法旋转、边界、无重叠、面积匹配。由纯函数校验，界面不能自行认定合法。
- 先用稳定有界装箱为旧货尝试新轮廓；若现有物件组合不能完整摆入，旧货使用兼容包装轮廓：原1格=2×2、原2格=2×4。这种旧货实例保留包装直到原物卖出/使用，不自动换新形状挤掉物品，不售卖包装、不收迁移费。合法旧4格组合必须无损装回4×4。
- 不够可靠或遇未知格式时停在可导出/恢复界面，禁止截断货物、清档、扩大成永久超大货舱或静默重置事件。
- 旋转/拖拽不得推进事件随机数。确认通过既有store.act()/revision进行原子校验；多标签中旧布局提交失效要提示并重新读取，不能覆盖另一标签的售货或事件收益。

## 2. ROUTE：把真正的航路画出来，不增加底栏按钮

### 2.1 保持四个主入口

保留港口/航行、航路、货舱、航记。修复route被映射到play：航路成为独立视图。状态导航不改变游戏phase或事件，往返查看地图不会结算一次飞行。

### 2.2 地图应看到的内容

- 起点港口、已经走过的实际航点、当前飞船位置、当前已生成的两个候选节点，以及从当前位置返港的虚线。
- 已走航段用实线+已访问标记，当前节点有飞船，两个可选下一站各有类型图标、短名称、风险和前进耗油。地图不能只是8个进度点或一张背景图。
- 点候选节点先选中并看同一张信息卡，再点“前往”；选择不会提前扣油。地图和原下一站卡引用同一个uid及quote()，不是两份可独立抽签的路线。
- 最多8站是上限，不要求地图永远显示8个具体地点。只显示已揭晓的历史和下一层候选，后方可以一个“未探明航区”淡背景，不暴露后续类型、物品、奖励或最优路线。
- 旧分支未选中后淡化为“未走过”，不可点击倒退刷事件。返航虚线表示按当前规则直接回港，不暗示反向重走每一站、逐站付费或途中再触发遭遇。
- 返航虚线/按钮明确显示当前homeCost()；候选卡显示quote().out、arrival、returnCost、free。保持渐进公式与返航储备，不恢复固定10油。
- 油量不足时保留禁用节点、油量差额与原因，不仅变灰；到8站时只保留合法返航/货舱操作，不生成第9站。
- 当前事件或pending装载未处理完时，地图可查看，但不能偷偷跳下一站。保留返回现场的直接入口。
- 随机组合在生成时保存，不因render、放大缩小、页面切换、刷新、重新打开而重新生成。当前history/legs可以用于迁移已访问轨迹；旧档缺失的历史未选分支不伪造。
- 建议按每次travel提交public node快照：nodeUid、类型/名称、深度、legFuel、from/to、已展示候选字段。路线显示不读取隐藏结果。

### 2.3 竖屏布局

在已有航路页用轻量SVG+HTML命中区绘制纵向航路：上方当前位置和返航费用，中间节点连线，下方选中航点详情/前往/返航。不能再让大块通用残骸插画把地图全部挤出首屏。历史较长可滚动，默认定位当前节点，返回视图保留位置。无需首版加入复杂缩放与宇宙旋转。

## 3. ICONS：事件、资源、选择、底栏使用同一套图标

- 新建共享的原创SVG/像素图标表，例如src/icons.js；图标随包内置，不依赖Emoji字体或外部CDN。统一viewBox、线宽/像素步进、配色与选中态，不混几套图库。
- 资源固定语义：燃料=油滴/油罐、耐久=船体盾牌、零件=机械零件、货舱=格状集装箱。顶部四项、选项代价、结果、港口报价和返航预估复用同一语义。
- 顶部保留“图标+短标签+实际数值”；燃料/耐久可用细条补充，不用条代替数字。低资源同时给图标/文字警示与数值，不能只靠变红。
- 航点类型映射已有数据：补给/维修/交易/残骸/漂流客舱/异常信号，各有不同图标；未知信号不提前显示实际藏品。
- 事件标题前放类别图标，正文继续简短；选项用“操作图标+明确动作+成本/风险图标”。只展示原模型实际已知的结果范围，不借加图标新增隐藏收益承诺。
- 结果卡把实际delta转成资源图标与带正负号的数值；不要只解析本地化字符串猜效果，使用结构化变化。
- 航记/港口结算也使用同一套。装饰图标aria-hidden，有动作的按钮保留可读标签，不能只靠一个陌生符号完成操作。
- 统一紫灰/暖金，不另做一套背包配色。保留顶部/底部安全区和设置入口；360×800/390×844、大字、短屏、实际宿主遮挡检查。
