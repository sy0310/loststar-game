## 一、确定的体验原则（不是候选）

1. **每艘船有一个连续的主货区**：优先能容纳整件大货，包括当前合法的旧版 `legacy16`（4×4）。不在主舱中挖孤立洞，不把设备边框/装饰当可用格。
2. **货舱差异来自主区比例、外围有效格与固定侧托盘的组合**：玩家从船型轮廓和实际拼图格中理解差别，不要求先配置容器位置、移动容器、叠背包或管理袋子附加属性。
3. **外围模块就是本船真实普通货物格**：升级后从锁定的边缘格变成可用格，格子与主区连接或具有明确的固定舱位边界。固定托盘可单独呈现，但容量算入该船已经购买的总格数，**不是额外送一个免费小仓库**。
4. **新手入门继续简单**：starter 基础完整4×4；其他船可以更宽/带边缘异形模块，但至少有连续好用的核心区域，能用原有的点选→旋转→放置、拖拽、自动整理与一键收下。
5. **维持四船已经买到的权益与费用**：starter `16→20→24`，scout `16→20→24`，cargo `20→25→30`，heavy `25→30`；已购升级次数、售价、燃油、船体、飞船/零件/债务不变。**同样标称容量不要求玩法上完全一样，但不允许旧合法货物被无故吃掉**。
6. **正文不增加新复杂度**：没有额外战斗、相邻加成、套娃背包、旋转整个货架、无限临时堆放区、长新手教程、额外主菜单入口。

## 二、技术形态：权威可用格mask + 连续主区 + 固定扩展区

以 `shipId + cargoLevel + topologyVersion` 索引唯一可信 mask。使用 `usableCells` 的个数计算容量，不能沿用 `width*height` 计算出“看似容量多、实际不可放”的数字。

推荐模型：

```text
shipHold = {
  shipId, cargoLevel, topologyVersion, width, height,
  usableCellMask,       // 模型权威：哪些格子真正可放货物
  mainHoldCells,        // 连续主货区，可容纳已有大件
  fixedTrayCells,       // 固定安装的边缘托盘；不是第二层无限仓
  lockedCells           // 未扩容区域：可显示轮廓，但不能落货
}
```

所有输入 `validate/solve/extend/place/rotate/preview/autoArrange/upgrade/equip` 使用同一权威mask；支持非矩形边界、触控错误回退、跨区域组合摆放的明确规则。**建议首版托盘与主区按一个统一坐标网格计算**：占格连续的多格物件若跨越可用相邻格且规则允许就能摆放，不要为图方便另造互不兼容的物件归属系统。若确有物理边框不能跨越，必须把禁止边缘在模型/视觉都说清，并通过求解率对照。

- **先保留可靠的4×4核心**，尤其 starter/scout；cargo/heavy 原有容量更多，可将部分有效格接在核心外侧形成船型特色。草案可以有侧托盘、尾翼或外缘格，但不能让合法 `legacy16` 没有任何放置位置。
- 推荐避免宽高超过6×6，不是数学上的强制上限；在360×800与390×844对照中，单格触控不能过小，旋转与确认仍需可见。
- 升级后mask新增格必须严格只增不减（原格子绝不可从有效变无效），尤其升级至 `24/25/30` 时不能重排玩家已有货物才算成功。
- 飞船绘制可以跟其外形不同，但**船外观和实际网格不是必须1像素1像素对应物理剖面**；保证形状合理、有视觉差异且真实可用即可。
- 旧自拟 `SHIP_HOLDS_MARKET_CANDIDATES.json` 的`shipHoldTopologies.*.baseRows`只是历史否决示意，**仍禁止直接拷入运行代码**；Codex 应在`v05`新建经过算法验证的`ship-holds-approved.json`或等价版本化配置，经测试冻结后供浏览器/Node共同读取。

## 三、旧存档、在途与切船保护是不可妥协的验收

- 当前仍使用独立存档库 `lostcargo.route-demo.v1`；如果新字段要求 schema7，迁移前在同一事务备份 schema6，容器不接受脏数据/无效mask；失败不覆盖旧档、不自动重开。
- **旧的矩形排列不能在升级瞬间被宣布非法**。对正在航行的旧档，记录固定的 `legacyRectHold` 有效形态直到该趟安全返港。不能对当前一趟路由或场景RNG重抽，也不能丢弃货物。
- 港口无损迁移：针对目标新船，先运行完整求解器重排**同一批物件**，验证货值、UID、来源、形状与库存完全等价，成功才在单次原子提交中切换新hold版本；失败保持原装备与旧合法排列，并给可理解的整理/售货选择。不能新增没有价格的临时“停泊仓”。
- 如果某船已有用户购买了扩容，迁移需要覆盖`cargoLevel`所有合法值。换回更小的船时，在**真正切换之前**核验当前物品可无损放下；失败不扣钱、不改变已装备船/燃油/耐久。
- 卖货、使用用品、救援、丢弃、取消装载/变更、跨窗口竞争或写盘失败都要释放合法格并保持事务一致。不能只检查截图，不验证纯模型。

## 四、Codex 的实施与验收顺序（B＋C 已批准，具体mask需测）

1. **冻结 v0.4.2 对照**：相同现有货物、同样船型与等级记录版A；读取 `CARGO_REFERENCE_RESEARCH.md` 的竞品原则，不能复制其原始素材/布局。
2. **制作 B＋C 组合的四船可点击/浏览器 QA 样板**：展示0级与所有升级等级的真实可用格，侧边/尾部固定模块，UI同屏、颜色清晰、自动整理/旋转都有效；不要再做A/B/C投票，A仅用于客观基线指标。
3. **几何纯模型+数据配置**：校验四船`16/16/20/25`及各级有效面积、mask连通性、完整4×4可容纳性、mask升级单调性，旧货`legacy4/8/12/16`及普通L/T/长条均不可穿过禁用格。求解器不能把“贪心没找到”说成完全放不下。
4. **QA对照与经济检查**：同组货的装入成功率、平均手动重排次数、空间碎片/浪费、获得物件数与实际收益；区分合理的船型差异与人为不友好的阻碍。**若某个具体mask明显卡住正常物品，Codex 可以在B＋C原则内调整，并留下前后证据，不必因每个像素再次要求产品选择。**
5. **接入与迁移**：提交model/UI/store变更，真实HTTP双引擎×360/390、大字/合成安全区、拖动/点选/旋转/自动整理、旧档/跨标签/断电模拟。不能为了新货舱破坏已完成的黑市/奇遇/任务或原渐进油耗。
6. **交付门槛**：仅当模型、存档、经济和视觉验收全通过，才在本机已授权流程生成新冻结ZIP、更新Mac同入口和TapTap新的开发自测；先保留原0.4.2固定包、私有备份和旧服务。PR保持Draft，禁止合并/提审/正式发布。
